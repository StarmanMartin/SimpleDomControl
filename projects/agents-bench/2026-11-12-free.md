### Findings of the third run

1. **SDC with the kit is now cheaper and faster than plain Django**: −11 % cost (3.71 vs 4.18 USD) and −33 % wall
   time (518 vs 777 s) over 18 runs each, at 18/18. The plain-Django run of the same day is a little more
   expensive than the second run (0.232 vs 0.218 USD per run), so part of the change is spread.
2. **The model-call gap is closed**: 7.3 vs 7.0 calls per run (8.6 vs 6.6 in the second run). SDC still carries
   12 % more context per call (framework knowledge: kit and skills), and the plain-Django agents write twice the
   output tokens.
3. **Per task, SDC wins where the feature is built in** (`mcp_token` 0.20 vs 0.44 USD, 31 vs 97 s; `model_review`
   0.16 vs 0.25 USD) and loses on small changes to existing code (`server_call`, `fix_counter`, `document`:
   +0.03 to +0.06 USD) and on the server-rendered list (`controller_list` 0.23 vs 0.15 USD).
4. **What the plain-Django results do not provide** (from the agents' final messages and the changed files):
   `model_review` pages need **no login** (3/3); `mcp_token` offers **one read-only tool** (3/3) in 10–15 new
   files, token expiry in 2 of 3; no WebSockets, live updates or REST API, and no package installed (0/18).
5. **Tests**: plain-Django agents changed tests in 15 of 18 runs, SDC agents in 5 of 18 (`controller_list` 3/3,
   `server_call` 2/3 — the new "After `new-controller`" section of the skill names where Django tests go).
6. Transcript split: SDC agents now read the skill and the code in one command (`cat …/SKILL.md; sdc_agent where …
   --show`); the analysis counts such a command as "skills", so project files drop to 1.4k characters per run and
   skills rise to 7.7k (`paper_sdc/figures/bench_tables.md`).

### Findings of the second run

1. **Same cost, SDC faster.** SDC with the (untuned) kit cost 3 % less than plain Django and took 26 % less wall
   time; across all 52 runs the cost per run is equal. The first run's "F is 6 % cheaper" was within the spread.
2. **The context hypothesis of the first run is not confirmed.** Agents read the same amount of project code in
   both stacks (3.7k vs 3.3k characters per run); generated boilerplate is not what fills the SDC context. The
   extra input comes from **framework knowledge**: the kit at the start (+1.8k tokens) and skills plus `sdc_agent`
   output (5.4k characters per run). Django is known from the model's training data, SDC has to be read.
3. **"Context per turn" (21k vs 13k) was a measurement artefact.** `num_turns` counts differently from model calls:
   the free agents bundle more tool calls into one model call (9.6 tool calls in 6.6 calls vs 9.0 in 8.6). Per
   model call the context differs by 12 % (25.3k vs 22.6k). The 46 % more input tokens of SDC come from ~30 % more
   model calls times ~12 % more context per call.
4. **Lever for SDC: fewer model calls, not shorter generated files.** Reading a skill costs one model call before
   the agent acts; the free agents start with one combined `cat` of the relevant files. Candidates: `AGENTS.md`
   asking to read the matching skill together with `sdc_agent where` in one step, and `sdc_agent where --show`
   printing the relevant file contents. The WP3.2 tuning (`452939a`) is not yet measured with transcripts.
5. **The plain-Django results do less than the SDC results** (checks test only the visible contract):
   - `model_review`: in all 4 free runs the agents reported that the new pages need **no login**; SDC models are
     invisible until `is_authorised` / `get_queryset` allow access.
   - `mcp_token`: the free agents wrote a 15-file app with **one read-only tool**, hashed tokens revocable in the
     admin; no expiry is mentioned. SDC's built-in MCP offers all models with read/write/delete per token, form
     schemas, expiry and an Origin check — at half the cost and a third of the time.
   - No free run added live updates, a general REST API or single-page navigation; no changed file touches
     WebSockets/Channels. None of the 22 runs installed a framework or package (only templates and vanilla JS).
6. **Free agents write more.** +74 % output tokens and +31 % changed files, partly because they wrote tests
   unasked (9 of 12 runs; 18 of 22 overall). Output tokens are priced far above cached input, so SDC's extra
   (cached) context and the free agents' extra output roughly cancel out in cost.

### Findings of the first run

1. **SDC with the agent kit costs about the same as plain Django** (2.17 vs 2.04 USD, within the run-to-run
   spread); SDC *without* the kit costs about twice as much. The kit is what makes SDC competitive for AI agents.
2. **SDC is cheaper where it has the feature built in.** MCP access with a token: 0.20 vs 0.36 USD and 30 s vs
   80 s — the free agent wrote a whole MCP app (token model, management command, views; 15 files). Fixing the
   broken widget and the model with validated forms also need fewer turns with SDC.
3. **Plain Django is cheaper for simple pages.** A list page costs 0.15 USD in plain Django vs 0.27 with SDC: one
   view and one template, against an SDC controller pair (view, template, JS, SCSS, organizer, URL).
4. **All free agents chose plain Django templates and vanilla JS** (`fetch`); none added htmx, React or Python
   packages. They wrote tests unasked in 9 of 10 runs (more output tokens).

## Not measured

The checks test the visible contract, not what each solution offers beyond it: SDC's controllers come with live
model sync, permission hooks, the AI assistant and an MCP server with privileges and revocable tokens; the free MCP
endpoints are hand-written (third run, finding 4, lists what was verified in the free results). Plain Django is
also far more common in the model's training data than SDC. One model; 3 runs per task in the third run.

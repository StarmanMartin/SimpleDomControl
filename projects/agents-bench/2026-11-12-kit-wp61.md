## Findings

1. **The agents follow the new rule.** Every `sdc_agent where` call used `--show` (16 of 16), mostly in the first
   command together with the skill (`cat .claude/skills/…/SKILL.md; python manage.py sdc_agent where … --show`).
2. **Fewer model calls, small effect.** 8.6 → 7.8 model calls per run (−9 %), input tokens −9 %, cost and wall time
   −3 %. SDC with the kit is now 7 % cheaper and 29 % faster than plain Django on the same tasks; the gap in model
   calls to plain Django (6.6) is halved, not closed. With 2 runs per task the per-task changes are within the
   spread (`fix_counter` got slightly more expensive). The effect includes WP3.2 and is not attributable to WP6.1
   alone; the start context did not change (21.1k vs 21.2k), so WP3.2 did not shrink it.
3. **Calls that are still spent on reading** (from the transcripts):
   - *Imports:* `--show` prints only the class, not the imports of the file; agents then ran `head -5
     library/sdc_views.py` or `sed -n 1,5p library/models.py` (server_call 2/2, model_review 2/2).
   - *After generating:* after `new-controller` / `new-model` the agents read the generated code in an extra call
     (controller_list 2/2, model_review 2/2).
   - *Edits after a failed edit:* a failed `Edit` / shell edit followed by a `Read` of the same file (server_call,
     fix_counter 2/2, document). The failure rate is the same as before (15 vs 18 failed calls) and partly comes
     from the `restricted` permissions (`sed -i`, `printf >>`).
4. Context per model call did not grow although `--show` prints more in the first call: the code is read once
   instead of twice.

### Findings of the follow-up run

1. **Model calls down again**: 7.8 → 7.2 per run (−16 % against the kit before WP6.1; plain Django 6.6). Input
   tokens −4 % (−13 % in total), tool calls 8.0 per run, fewer failed calls (12).
2. **Cost did not follow** (2.49 vs 2.45 USD, within the spread): one `controller_list` run took 15 turns and
   0.33 USD (see 4). Context per call grew slightly (26.1k), because the first answer now carries more code.
3. **Fewer reads after `--show` and `new-model`.** `server_call` read no imports any more (2/2). In
   `model_review` both agents ran skill, `where Book --show` and `new-model library Review` in **one** command;
   run 1 then edited directly, run 2 still read parts of `models.py` and `forms.py` once (`sed -n 1,12p …`). Both
   finished in 4–5 turns (median 0.18 USD, 26 s; free 0.25 USD, 42 s).
4. **Generated code did not save the read in `controller_list`**: after `new-controller` the agents still ran
   `git diff` and looked for a `book_list.html` next to the JS, and searched the `sdc_core` sources and the skills
   for `register(` (also in the earlier runs). The skill does not tell them what to change in the generated
   JS for a server-rendered list; this task is now the most expensive one for SDC (0.29 vs 0.15 USD free).

## Controller skill update, 3 runs per task (2026-11-12)

Changes: `sdc-controller` skill section "After `new-controller`" (no JS change needed for a server-rendered page,
the second argument of `app.register`, edit the template in `templates/<app>/sdc/`, not the link next to the JS,
where tests go, checking the HTML without a browser); `new-controller` no longer lists the git-ignored template
link (`sdc_cc` symlinks the template into the JS folder for editors; agents read it and tried to write to it);

### Findings of the skill update

1. **`controller_list` got cheaper**: 0.29 → 0.23 USD, 44 → 30 s; no run searched the `sdc_core` sources for
   `register(` or wrote to the template link any more.
2. **The skill nudges agents to write Django tests**: 5 of 18 runs changed `tests.py` (`controller_list` 3/3,
   `server_call` 2/3; before 0–2 of 12). `server_call` rose to 0.23 USD (11 turns), mostly through writing and
   fixing these tests. Plain-Django agents changed tests in 15 of 18 runs, so the products became more alike;
   whether the skill should mention tests at all is a separate decision.
3. **Overall per run unchanged** against the follow-up (0.206 vs 0.207 USD, 7.3 vs 7.2 model calls). Over the
   whole of WP6.1, per run: model calls −15 % (8.6 → 7.3), input tokens −13 %, cost −2 %, wall time −4 %.
   Cost moves less than tokens because most input is cached.

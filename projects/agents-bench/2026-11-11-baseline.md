## Findings

1. **Turns drive the cost.** 96 % of all input tokens are cache reads: every turn re-reads the growing context.
   Cost and input tokens scale with turns × context size, so fewer turns (and less reading per turn) is the main
   lever; output tokens are only ~1 % of the tokens.
2. **Framework knowledge is the most expensive part.** `fix_counter` costs about 2–3× the other tasks (38 turns,
   1.2M input tokens). The agent could not read the SDC client source (outside the project, no `node_modules`) and
   had to guess how SDC binds event handlers; it said so in its final message. → `sdc-controller` skill with the
   lifecycle and event pitfalls (M2), `sdc_agent check` reporting arrow functions in the constructor (M1, WP1.4).
3. **Wiring a controller costs ~27 turns although `sdc_cc` does it.** All runs found and used `sdc_cc` (the
   generated file set appears every time), but needed many turns to discover it and the file layout. →
   `sdc_agent new-controller` / `where` (M1) and `AGENTS.md` naming the commands (M2).
4. **Running `manage.py` changes tracked files.** `sdc_core`'s `AppConfig.ready()` rewrites `Assets/.sdc_env` and
   `Assets/.sdc_python_env` in DEBUG; agents notice the diff and spend turns reverting it. → write them only when
   the content changes (add to M1).
5. **Simple configuration tasks are already cheap** (`model_review`, `mcp_token`, `document`: 16–19 turns,
   ~0.3 USD). The kit should not make them more expensive (always-loaded context ≤ ~800 tokens).

## Target for M3

Same tasks, model and settings with the kit: ≥ 30 % fewer total input tokens (≤ 7.3M of 10.4M) and fewer turns
per task at 18/18 success; the largest gain is expected for `fix_counter` and `controller_list`.
